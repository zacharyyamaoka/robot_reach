H · What is the FK cloud, and what do its colours mean?

Yes — the FK cloud is what sized the voxel grid. Verified in analyze.py / sampling.py / arm.py and the saved arrays:

  1. Sample joints: 20,000 joint vectors, uniform inside the joint limits (seed 0). FK gives each one a tool position.
  2. Make the box: the bounding box of all those positions (colliding ones too) is the grid box: 1.90 × 1.90 × 1.90 m. The step is the extent ÷ 18 = 106 mm, so 19 × 19 × 19 = 6,859 grid points.
  3. Ask IK there: every grid point × the 132 shared orientations × every IK branch. That is the voxel map; the cloud is only drawn for context.

Colours are each sample's joint-space check (Arm.check, the first failure wins: joint limit → FK fails → collision → torque → singular → OK):

  • OK 8,903
  • collision 9,895 — for the UR5e the only collision model is the floor: some skeleton point is below z = 0. That is why the lower half of the cloud is red.
  • singular 1,202 — manipulability under 1 % of the arm's typical (95th-percentile) value.
  • Orange (over torque) and grey (cannot close) never occur on the UR5e: it has no torque limits or closed loop in this model.

The viewer draws 12,000 of the 20,000, evenly thinned. Gap: the Workspace legend explains the voxel colours only, so nothing on screen explains the cloud's. Fix: when FK cloud is ticked, add a second legend line “cloud: ● OK ● collision (floor) ● singular”.

A · Choosing which IK solution types to include

You: “fix a solution type … select whether I want to support elbow up or down, wrist up or down, the other thing … all 8 or any combination … a standard Robot MSG that allows you to name the different IK solutions … so you can automatically generate these check box UI.”

The type (prototype: docs/proposals/ik_branches.py). One small frozen message names the questions; the arm tags every solution with its answers. All three UIs below are generated from UR5E_BRANCHES.ui_spec() alone; nothing in them knows it is a UR.

@dataclass(frozen=True)
class BranchAxis:
    name: str                    # "elbow"
    options: tuple[str, ...]     # ("up", "down"): option i is tag value i
    joint: str = ""              # the joint that flips it, shown as "elbow (J3)"
    rule: str = ""               # how a solution is tagged, in plain words (tooltip)

@dataclass(frozen=True)
class IKBranches:                # would live in robot_msgs.manipulation, beside NamedPose
    arm: str
    joint_names: tuple[str, ...]
    axes: tuple[BranchAxis, ...]
    def type_of(self, tags) -> Array        # (N, n_axes) answers -> (N,) type index
    def type_name(self, i) -> str           # "shoulder front · elbow up · wrist J5+"
    def allowed(self, **choices) -> Array   # allowed(elbow="up") -> (n_types,) bool
    def ui_spec(self) -> dict               # what a viewer draws: axes, options, types

UR5E_BRANCHES = IKBranches("ur5e", JOINTS, (
    BranchAxis("shoulder", ("front", "back"), "shoulder_pan", "front: the wrist is in front of the pan axis"),
    BranchAxis("elbow", ("up", "down"), "elbow", "up: the elbow is above the shoulder-to-wrist line"),
    BranchAxis("wrist", ("J5+", "J5−"), "wrist_2", "the sign of wrist_2 (J5): the wrist flip")))

# beside ReachMap.sol_q: one tag per solution, computed from its joints by the arm
ReachMap.sol_type: Array   # (K,) uint8, IKBranches type index
Arm.branches: IKBranches | None ;  Arm.tag(q) -> (N, n_axes)

Why tags come from the posture, not the solver's slot (measured on 20,000 random UR5e solutions): with the shoulder on one side, slot “elbow +” is physically elbow-up 99.5 % of the time; on the other side it is elbow-up 0.7 % of the time. A checkbox wired to the slot would mean the opposite half the time, and a numeric IK (the URDF path) has no stable slots at all. Solutions per type: 152,358, 153,846, 98,352, 98,796, 153,810, 152,358, 98,856, 98,502.

What the filter does on this arm (measured): elbow-up only keeps every level (reachable 1,955 · 4-DOF 1,396 · hemisphere 827 · dexterous 699); front + elbow up keeps reachable 1,952 · 4-DOF 1,396 · hemisphere 775 · dexterous 656; one single type keeps reachable 1,941 · 4-DOF 1,364 · hemisphere 546 · dexterous 529. With only a floor check, the UR's elbow pair is interchangeable; the filter matters once a real collision model or a task (“never flip the wrist”) is in.

B · Joint ranges: limits vs what the working solutions use

You: “histogram or violin plot could be clearer than using the colour, as height difference is easier to perceive than colour.” Also: always write (J1/J2/…) beside the joint name.

All five from the same 1,006,878 working UR5e solutions. Finding: every joint's solutions sit inside about ±180° (shoulder_pan -178…+178° · shoulder_lift -178…+178° · elbow -158…+157° · wrist_1 -179…+178° · wrist_2 -174…+174° · wrist_3 -180…+178°) although the limits are ±360°: the IK returns angles wrapped to ±180° and the library only uses the ±360° twin when a value is outside the limits. So the “used range” shows the solver's habit, not a need — the plot should say so, or draw ±360° joints on a −180…180° axis. Likewise wrist_3's spikes every 60° are the six sampled rolls, not a preference of the arm.

The metadata the result must carry


Today result.json["config"] holds: step 0.1057 m (one number, not XYZ), box centre/size, n_fk 20000, floor_z 0.0, singular_tol 0.01, w_ref, seed 0, and orientations: 132 — only the count. The tilt step, roll count, max tilt and approach that made those 132 are not recorded, nor the round-trip tolerances (they sit in the npz's meta), the arm's version or the code commit. So a result cannot yet fill the F2 card by itself. Proposed:


@dataclass(frozen=True)
class ReachSettings:
    """What a reach result was computed with. Saved as result.json["settings"]; the viewer's
    Workspace card is filled from it, and a change of digest() is what lights Compute workspace."""
    # 1 robot
    arm: str                                   # "ur5e"
    arm_source: str                            # "robot_reach.robots:ur5e" or the URDF path
    arm_digest: str                            # sha256[:16] of the URDF text / factory kwargs
    ik: str                                    # "closed form, 8 branches" | "numeric DLS, 8 seeds"
    # 2 where to look: automatic, recorded not chosen
    fk_samples: int = 20_000
    seed: int = 0
    box_center_m: tuple[float, float, float] = (-0.006, 0.009, 0.166)
    box_size_m: tuple[float, float, float] = (1.897, 1.900, 1.902)
    # 3 resolution: the only things a person sets
    voxel_m: tuple[float, float, float] = (0.1057, 0.1057, 0.1057)
    tilt_step_deg: float = 45.0
    roll_step_deg: float = 60.0
    max_tilt_deg: float = 180.0                # a full analysis always asks everything
    approach: tuple[float, float, float] = (0.0, 0.0, -1.0)
    # checks
    floor_z_m: float | None = 0.0
    singular_tol: float = 0.01                 # of w_ref, the arm's 95th-percentile manipulability
    pos_tol_m: float = 1e-4
    rot_tol_deg: float = 0.057
    # provenance (not part of digest)
    library: str = "robot_reach 0.1.0 @ <commit>"
    computed_at: str = ""
    seconds: float = 14.0

    def digest(self) -> str: ...              # hash of sections 1-3 + checks: equal digest = same result
